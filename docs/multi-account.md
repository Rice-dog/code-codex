# Multi-account Tasks (temporarily suspended)

**Current product status:** `MULTI_ACCOUNT_AVAILABLE=false` hides this plugin and prevents its runtime from loading or starting. Account selection, quota/assets queries, switching and automatic continuation do not run, even if an earlier installation saved enabled=true. Code, exact package cache, account files and preferences remain available for a later explicitly requested restoration. Safe hot suspension waits for active work, restores idle native endpoints and retires selectors/adapters; it does not stop or replay a task. The following sections document retained candidate implementation, not an enabled public feature.

This optional Developer Tools plugin adds an account selector beside the native model control. Each local conversation remembers its selection; finish the current response or confirm Stop before changing accounts. Automatic continuation is off by default; it requires the explicit switch in this plugin's settings. Selecting an execution identity leaves the official GUI login unchanged.

Pin the plugin to add its existing icon between the market button and version in the footer. Clicking it opens the market's Tools category and this settings panel, without enabling or disabling the plugin. Pins from all categories share that shortcut strip; extra icons go in its overflow menu.

## Optional continuation after quota exhaustion

Enable **Continue with the next account when quota runs out** to continue an unfinished task after a confirmed `usageLimitExceeded` failed turn. The order is the official account first, followed by authorized connections in their original addition order. Starting at account two tries two, three, then one. Each task traverses the snapshot of its account list at most once; normal completion ends the traversal.

Before preparing a candidate, the plugin reads its fresh quota without sending inference. Both five-hour and weekly remaining values must be known and positive. Exhausted, removed, unreadable or unknown-quota accounts are skipped. A fresh check is not a promise that the remaining allowance will finish a task. If the new account also exhausts its allowance, the traversal continues; all-unavailable ends with one diagnostic.

An eligible account is prepared through the same native history, workspace, permission and tool checks as manual selection. The native conversation manager then receives one new continuation message asking it to preserve completed work and inspect the last interrupted action. The original prompt, attachments, tool output, old delivery callbacks and tool commands are not replayed. A continuation is a new inference turn and uses the selected account's normal allowance.

User Stop, opt-out, logout/owner changes, normal completion, other failures, unknown delivery and unverified prior execution outcomes prevent further automatic sends. Temporary `rateLimitExceeded` throttling is distinct from exhausted usage and does not trigger this feature. Pending preparation may finish committing an account after opt-out, but cannot send a continuation; the visible selection remains consistent with that committed identity. The traversal is memory-only and never resumes a task automatically after restart.

Enable the plugin, open its adjacent settings panel, click the final plus tile, and authorize through the official browser page. Connected rows show avatar, email, two quota windows, a sign-in dot and an actions menu. The current official account has a small monitor marker. The panel subtitle appears below the title; no redundant category/footer or hover titles are added. Labels and percentages are separate right-aligned, content-sized columns with a 5 px gap in the panel, composer button and account menu; no fixed minimum width stretches the space between them. The panel repositions when asynchronous rows change its height or the window resizes.

The continuation setting is a sliding switch, initially off, with native keyboard and focus behavior. Before each explicit Send in a shared conversation, a serialized read-only reconciliation confirms the owned executor is idle or has exited. Only then can stale UI running markers be cleared; real activity, unverified event streams, failed checks and concurrent sends remain blocked. Stop during this check cancels the unsent request. An exited executor requires fresh preparation, and an unverified previous outcome is reported without replaying it. Runtime `account.admission` diagnostics record bounded state, reason and duration, never message content or credentials.

## One project and one official conversation

An account is an execution identity, not a separate copy of the project or conversation. The native service validates the existing official thread ID, history path and workspace, then resumes that same ID and file in one executor for the logical conversation. Changing identity replaces the executor's in-memory authentication between turns. It does not create an account-specific thread, inject copied messages or serialize the full conversation into plugin snapshots. Native history pagination remains available. Old plugin snapshots are retained as historical user data but are no longer read or written for execution; old child-only outputs are not silently merged into official history.

Normal official conversations remain on the original execution path until first shared. After sharing, returning to the official identity uses the same executor and history. Disabling hides the selector and selects the official identity; a narrow shared-history route remains until the document ends, so disabling cannot return that conversation to a stale in-memory actor. Idle native account leases are released before hot activation even when the plugin is disabled; active independent tasks block handoff. Active turns prevent disabling or switching, while the account menu remains readable and available for inspecting quotas. Selecting an identity prepares authentication, the same history and native permissions before committing the selection; a failed preparation keeps the previous selection. Preparation progress does not run inference. New conversations without an ID retain a draft selection and still require preparation when their history is established.

Credentials remain native. Independent sign-in and refresh use an isolated official backend and its encrypted credential storage. The qualified backend's token export is consumed only by the native credential module; tokens do not enter renderer responses, events or routing metadata. The executor uses the official in-memory token authentication mode. The renderer cannot invoke account authentication/export methods or choose arbitrary history paths.

## Login lifetime

Minimizing, hiding, temporary disconnection, or completely exiting the program does not sign out child accounts. Reopening while the official account is still A restores A's saved connections and selections. An unconfirmed task outcome must be reconciled before another turn; it is never replayed automatically.

An explicit official desktop logout ends that login's child connections. A core-installed guard observes the current owner, completes native child cleanup, then forwards the official logout once. Cleanup persists an ended-session marker before stopping owned executors and deleting child credentials, so an interrupted cleanup cannot restore revoked connections. A cleanup failure retains the marker and reports a retryable error. Logging back into A after explicit logout starts with no children; logging into C does not display A's children. Closing a browser login page is not an official desktop logout event.

Upgrade and retained uninstall preserve data. Standalone explicit purge removes only credential targets derived from verified owned child homes, supporting both legacy and encrypted-store targets. Project history and official main-account credentials are outside child cleanup. Direct MSI explicit credential purge is not yet integrated with this cleanup.

## Quota

Check login and Check task status keep the account actions menu open. The clicked row shows Checking with a small spinner, then the actual sign-in or task-state result for four seconds. Repeated clicks are blocked while pending; failures show an English retry message and preserve the original diagnostic. Task checking distinguishes an idle account, a still-running backend and cleared stale state; it does not stop tasks or verify their output. Locale changes and refresh preserve feedback. Closing or disposing the menu invalidates late feedback, and reduced-motion preferences disable rotation. These checks do not send model requests.

All authorized identities receive an initial independent read, with at most two requests concurrently. Unused accounts retain their last successful values rather than being polled every minute. A confirmed completed/failed/interrupted turn refreshes the identity it used. Known reset boundaries, explicit sign-in verification and reauthorization can also refresh it. Reads never send inference or consume reset credits.

During execution, quota notifications from that executor update its selected identity immediately, including notifications without a thread ID. The active identity alone has a throttled 30-second read fallback; unused accounts are not polled. Newer notifications cannot be overwritten by an older pending read. Reset dates still reuse the cached server timestamp rather than initiating another request.

The display is the account's codex quota, not a guessed separate quota for each model. Windows are identified by their actual durations: five hours and one week. Used percentage is converted to remaining percentage. Missing, invalid or expired data displays an em dash, never a guessed zero. Refreshing or a temporary read failure preserves a still-valid previous value. Failures have a bounded retry delay; changing the observed owner clears the memory-only cache and rejects late results.

The settings panel and expanded account menu show each window's server reset time in the machine's local timezone; the compact composer button keeps percentages only. Full windows display Full, and missing future server timestamps display Reset time unknown. Each window caches the first consumed observation in its cycle, reusing it until full or expired. Reset times come from the existing quota response, with no separate request or display-driven polling. Reopening the runtime rebuilds this owner-scoped memory cache through the normal initial quota reads.

Choosing an account keeps the menu open. A subtle highlight, small spinner and short real preparation stage appear on the target row. The selected check moves only after success; a failure stops the spinner, retains the old selection and shows a bounded English error code on the target row. Full diagnostics remain in the existing runtime log. Row heights stay stable, keyboard focus survives phase updates, and reduced-motion preferences disable rotation. The compact trigger has no progress bar.

## Boundaries and verification

The adapter is qualified against the exact official build and two asset hashes in `resources/account-host-contract.json`. Unsupported builds fail closed. Fixed Bridge actions recheck owner, workspace and thread identity. Only bounded current inputs use chunk transfer; full history does not cross the Bridge. The existing 96 KiB frame budget remains, with sequential owner/epoch-bound chunks and a 4 MiB current-request limit. Unknown Send results and event gaps require reconciliation, not silent fallback.

One runtime home per logical conversation holds a small projection of the existing tool configuration, excluding model-provider credentials. It links the existing skills, plugins and rules instead of copying those resources. The separate runtime home avoids the official actor writer-lock collision; the official thread ID, history file and SQLite directory remain shared. Account changes reuse this same runtime, rather than creating per-account history copies. Relative MCP commands and Node are resolved from the original tool PATH. Verified official executable companions are staged with the main binary and shared within the owning core. Native permission selections and bounded thread/turn settings updates are forwarded instead of replacing them with a fixed policy. This does not establish parity for every desktop-only dynamic connector or capability; those require separate validation. Validation separates production policy/adapter fixtures, Chromium layout tests, real backend credentials and same-history continuation, confirmed interruption, real user logout, and local package/install checks. A real backend marker/Stop test does not prove all GUI approval, tool, attachment, multi-window or reboot workflows. Public distribution remains blocked until exact pending plugin assets are published and the publication gate passes. Local installation and cache import do not prove public download availability.

Workspace verification compares native directory identity, including equivalent Windows verbatim/ordinary paths. It rejects missing or different project roots before dispatching a turn.

### Preparation failures and native permission profiles

Selecting an account for an existing conversation prepares authentication, the same history and the native permission selection before committing the identity. Built-in profiles (`:read-only`, `:workspace`, `:danger-full-access`) retain their native identifiers. Resolved sandbox state is not sent alongside a selected profile. Quota exhaustion ends the failed turn; switching and retrying are explicit user actions.

Registry admission is bounded to 15 seconds and preparation to 70 seconds. Real phase progress is available independently of the registry lock; English runtime diagnostics include the operation ID, phase, elapsed time and whether a task was sent. Failed or timed-out preparation retains the previous selection, invalidates partially changed executor authentication and releases the composer's preparation lock while preserving the draft. No task is automatically replayed. Permission updates during preparation wait for its result; a running response keeps the account menu readable and inspectable without allowing identity changes.

User Stop supports native background-terminal cleanup and observes interruption for up to eight seconds, then retires the plugin-owned executor to fence stale events and requests. Only confirmed process exit unlocks the conversation; an unconfirmed last task outcome is reported explicitly. A subsequent turn resumes the same official history through a fresh preparation. The official GUI process is preserved.

The event stream acknowledges delivered cursors, merges only adjacent unsent matching text deltas, and immediately drains bounded backlog pages. A real overflow includes cursor and queue diagnostics and stops repeated polling of the obsolete cursor. Other conversations continue; explicit Stop remains available for recovery. Unsupported controls report the exact bounded method and relevant state. An abandoned lock after restart is reconciled read-only before activation; a live task still prevents handoff.
